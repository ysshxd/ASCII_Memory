# ASCII 코드 작성 기준

현재 `src/`의 React·TypeScript·CSS 코드에 맞춘 작성 규칙이다. 코드를 읽을 때 구조와 의도가 바로 보이도록 정렬하고, 필요한 책임만 나누며, 불필요한 로직과 추상화를 만들지 않는다.

## 1. 들여쓰기와 기본 스타일

- TS·TSX·JS·JSON·YAML·CSS는 공백 2칸을 사용한다. 탭을 섞지 않는다.
- UTF-8, LF, 파일 끝 개행 1개를 사용한다. 줄 끝 공백을 남기지 않는다.
- TS·JS 문자열은 작은따옴표, JSX 속성은 큰따옴표를 사용한다. 세미콜론은 현재 코드처럼 생략한다.
- 줄 길이는 100자를 기준으로 한다. 짧고 읽기 쉬운 코드를 이유 없이 여러 줄로 늘이지 않는다.
- 연산자와 쉼표 뒤에는 필요한 공백을 둔다. 수동 공백으로 변수나 속성의 열을 맞추지 않는다.
- 포맷터가 도입되면 이 기준을 설정으로 고정한다. 현재 Prettier·EditorConfig 설정은 없다.

## 2. 줄바꿈과 빈 줄

- import 묶음과 본문 사이, 타입·상수·함수·컴포넌트 사이에는 빈 줄 1개를 둔다.
- 함수 안에서는 검증, 계산, 상태 변경, 반환처럼 의미가 바뀌는 지점에 빈 줄 1개를 둔다.
- 모든 문장 사이에 빈 줄을 넣거나 빈 줄을 여러 개 연속으로 넣지 않는다.
- 짧은 함수 호출·객체·JSX는 한 줄로 유지한다. 길어지거나 중첩 때문에 읽기 어려울 때 줄을 나눈다.
- 여러 줄로 나눈 인수·속성은 같은 깊이로 정렬하고 닫는 괄호는 시작 구문에 맞춘다.
- 문자열·이름을 억지로 쪼개거나 단순한 속성마다 불필요한 줄바꿈을 만들지 않는다.

```tsx
const [count, setCount] = useState(0)

function handleIncrement() {
  setCount((currentCount) => currentCount + 1)
}

return (
  <button type="button" className="counter" onClick={handleIncrement}>
    Count is {count}
  </button>
)
```

## 3. 괄호·중괄호·JSX

- 표현식 전체를 의미 없이 여러 겹의 괄호로 감싸지 않는다.
- 연산 우선순위를 분명히 하거나 서로 다른 논리 연산을 구분하는 괄호는 유지한다.
- `if`, `else`, 반복문은 본문이 한 줄이어도 중괄호를 사용한다. 흐름을 한 줄에 압축하지 않는다.
- 화살표 함수의 매개변수 괄호는 현재 코드처럼 유지한다. 단순 반환은 불필요한 중괄호·`return`을 생략한다.
- 여러 줄 JSX 반환에는 `return (...)`을 사용한다. 자식이 없는 요소는 `<Component />`로 닫는다.
- 단일 요소를 감싸기만 하는 Fragment나 `div`는 추가하지 않는다. 여러 형제를 묶거나 레이아웃·의미상 필요한 경우에만 사용한다.

```ts
// 불필요한 괄호와 조건 중복
const isReady = ((count > 0)) ? true : false

// 조건 자체가 boolean을 반환한다
const isReady = count > 0

// 서로 다른 논리 연산의 묶음은 분명하게 유지한다
const canSubmit = isValid && (hasChanges || isRetry)
```

## 4. 조건문과 로직

- 실패·예외 조건을 먼저 처리하고 early return으로 중첩을 줄인다.
- 중첩 삼항식은 사용하지 않는다. 단순한 두 값 선택만 삼항식으로 작성한다.
- 복잡한 조건은 의미 있는 변수나 함수로 나눈다. 단순 비교에 이름만 붙인 변수를 계속 늘이지 않는다.
- 한 줄에 대입·분기·부수 효과를 섞지 않는다. `&&`로 상태 변경을 실행하기보다 `if`를 사용한다.
- 단순한 작업은 직접 구현한다. 같은 배열을 불필요하게 여러 번 순회하거나 복잡한 `reduce`로 압축하지 않는다.
- `if (condition) return true; else return false`처럼 조건값을 그대로 돌려주는 분기는 제거한다.
- 이미 검증된 값에 같은 검사를 반복하지 않는다. 실제 실패 가능성이 있는 위치의 검사는 유지한다.
- 오류를 빈 `catch`나 근거 없는 기본값으로 감추지 않는다.

## 5. 이름과 함수

- 변수·함수는 camelCase, 컴포넌트·타입은 PascalCase를 사용한다.
- boolean은 `isLoading`, `hasChanges`, `canSubmit`처럼 판단 내용을 드러낸다.
- `data`, `temp`, `manager`, `utils`보다 `selectedFile`, `previewText`, `formatFileSize`처럼 역할을 드러낸다.
- 이벤트 함수는 `handleSubmit`, 전달하는 콜백 prop은 `onSubmit`처럼 구분한다.
- 함수는 하나의 작업을 맡는다. 이름에 드러나지 않는 상태 변경이나 다른 작업을 끼워 넣지 않는다.
- 한 번만 쓰는 짧은 표현식을 의미 없이 함수로 감싸지 않는다. 이름이 의도를 설명하거나 복잡한 작업을 분리할 때 추출한다.
- 사용하지 않는 변수·함수·import·주석 처리한 코드는 남기지 않는다.

## 6. 컴포넌트 분리

- `src/main.tsx`는 앱 마운트, `src/App.tsx`는 화면 구성과 컴포넌트 조립을 맡는다.
- 컴포넌트에 화면 표시와 무관한 복잡한 계산·요청 처리·여러 기능의 상태를 몰아넣지 않는다.
- 독립적인 역할이 있거나, 같은 의미로 재사용되거나, 자체 상태·상호작용 때문에 읽기 어려워질 때 분리한다.
- 줄 수만으로 쪼개지 않는다. 제목 하나·`div` 하나를 파일로 만드는 식의 과도한 분리를 하지 않는다.
- 같은 모양이어도 역할과 변경 이유가 다르면 억지로 공통 컴포넌트로 합치지 않는다.
- 작은 기능 전용 컴포넌트는 같은 파일에 둘 수 있다. 독립적으로 관리하거나 다른 곳에서 사용해야 할 때 별도 파일로 옮긴다.
- prop 수십 개와 boolean 옵션으로 모든 화면을 처리하는 범용 컴포넌트를 만들지 않는다.
- JSX 안의 단순한 이벤트는 인라인으로 둘 수 있다. 여러 단계의 처리는 이름 있는 핸들러로 뺀다.

## 7. React 상태와 훅

- 입력값·열림 여부처럼 화면에 필요한 상태는 사용하는 컴포넌트 가까이에 둔다. 실제 공유가 필요할 때 상위로 올린다.
- 기존 값으로 계산할 수 있는 값을 별도 state로 중복 저장하지 않는다.
- 단순 계산을 위해 `useEffect`와 `setState`를 연결하지 않는다. Effect는 외부 시스템과 동기화할 때 사용한다.
- `useMemo`, `useCallback`, `memo`는 측정된 비용이나 필요한 참조 안정성에 근거해 사용한다. 모든 값과 함수에 습관적으로 붙이지 않는다.
- 커스텀 훅은 재사용되는 상태 로직이나 독립된 복잡한 흐름을 분리할 때 만든다. 훅을 한 번 감싸기만 하는 훅은 만들지 않는다.
- 목록의 key는 안정적인 식별자를 사용한다. 변경되는 목록에 임의 값이나 배열 인덱스를 습관적으로 사용하지 않는다.

```tsx
// count로부터 계산되는 값은 state와 Effect로 복제하지 않는다
const [count, setCount] = useState(0)
const isEmpty = count === 0
```

## 8. 파일·import·스타일 정리

- 현재 구조를 기준으로 필요한 파일만 추가한다. 사용처 없는 폴더·공유 계층을 미리 만들지 않는다.
- 기능 전용 코드와 스타일은 가까이 둔다. 두 번째 실제 사용처나 명확한 공통 책임이 생기면 공유한다.
- import는 외부 패키지, 프로젝트 내부 코드·자산, 스타일 순서로 묶는다. 다른 묶음 사이에는 빈 줄 1개를 둔다.
- `src/index.css`에는 전역 토큰·기본 요소·공통 레이아웃을, `src/App.css`에는 해당 화면 스타일을 둔다. 별도 컴포넌트의 전용 스타일은 해당 파일 가까이 둔다.
- CSS는 선택자마다 블록을 구분한다. 같은 선택자·속성을 불필요하게 반복하거나 과도한 중첩·`!important`로 덮어쓰지 않는다.
- 실제로 같은 의미인 색상·간격·계산은 공통 값으로 묶는다. 한 번만 쓰는 값까지 모두 상수 파일로 옮기지 않는다.

## 9. 불필요한 코드와 추상화 금지

- 현재 요구에 없는 로직·옵션·확장 지점을 미리 구현하지 않는다.
- 단순 함수로 충분한 일에 Factory·Manager·Wrapper·클래스 계층을 만들지 않는다.
- 같은 값을 여러 계층으로 전달하기만 하는 함수·컴포넌트는 만들지 않는다. 실제 책임을 가진 경계만 유지한다.
- 타입 추론이 명확한 지역 변수에 반복적인 타입을 붙이지 않는다. props·외부 경계·중요한 계약에는 타입을 명확히 둔다.
- `any`, 타입 단언, non-null 단언으로 문제를 덮지 않는다. 필요한 경우 실제 근거와 적용 범위를 확인한다.
- 주석으로 코드 동작을 그대로 읽어주지 않는다. 선택 이유와 비명백한 제한만 설명한다.
- 가독성을 해치는 장식용 주석, 의미 없는 임시 변수, 불필요한 타입·객체 복사와 래퍼를 제거한다.

## 10. 수정 후 확인

- 들여쓰기·줄바꿈·괄호가 일관되고 한눈에 흐름이 보이는가.
- 컴포넌트·함수에 서로 다른 책임이 섞이거나 반대로 지나치게 쪼개지지 않았는가.
- 불필요한 조건·state·Effect·메모이제이션·추상화가 없는가.
- 이름만으로 역할을 이해할 수 있고 죽은 코드가 남아 있지 않은가.
- 코드 변경 시 `npm run lint`, `npm run build`를 확인한다. 화면 동작을 바꿨다면 해당 동작도 확인한다.

이 기준은 일반 구현 코드에 적용한다. 외부 생성물이나 원문·공백·바이트 보존이 필요한 파일은 별도로 취급한다.
